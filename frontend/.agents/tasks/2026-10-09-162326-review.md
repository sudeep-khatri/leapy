# LipiAI Chat Feature

The chat feature adds a three-mode conversational interface for Nepal Bhasa and Nepali, with Aksharamukha-powered script conversion that renders Devanagari input as Rañjanā glyphs on the wire. The implementation is split cleanly across a service layer (`chat-service.ts`), a file-based route (`routes/chat.tsx`), and a React component (`chat-interface.tsx`). The Aksharamukha integration is deliberately shallow — only a font swap for Rañjanā modes, no attempt at Unicode script conversion beyond what the API returns, which is the correct approach given Rañjanā's non-Unicode status. Watch for: the `convertScript` call passes user input text to the Aksharamukha public API as a query parameter, which has URL-length implications for long messages (confirmed).

**Verdict**: APPROVED

## High-level view

The service layer is well-structured with a clean separation between the short-circuit path (`source === target` skips fetch), graceful degradation on API failure, and the AI chat fetch. The `endpoint` parameter defaulting to `import.meta.env['VITE_LIPIAI_CHAT_URL']` using bracket notation satisfies the `noUncheckedIndexedAccess` / `exactOptionalPropertyTypes` requirement and mirrors the inscription-analysis pattern for testability.

The UI component correctly uses functional `setMessages` updates to avoid stale-closure bugs across the two sequential async calls, aborts previous in-flight requests on re-submit, and separates `AbortError` from real errors silently. The `handleSubmit` is wrapped in `useCallback` with `[inputText, mode, messages]` deps — this is correct but means a new function reference on every keystroke; not a performance concern at this scale.

The nav order in `lipiAI-shell.tsx` is About → Chat → logo-mark → Community, matching the spec exactly. The Noto Sans Newa / Noto Serif Tibetan Google Fonts link is present as the second stylesheet in `__root.tsx`, after the EB Garamond link.

The CSS uses `oklch()` throughout with the eight `--chat-*` vars. The Rañjanā font is loaded from the jsdelivr CDN with `font-display: swap`, which falls back gracefully to `var(--font-body)` if the CDN is slow.

The three CHAT_MODES have the correct ids, labels, fontClass values, and `aksharaSource`/`aksharaTarget` pairs. The devanagari mode uses `source === target` (`Devanagari`→`Devanagari`), so `convertScript` returns the input immediately without a network call.

<details>
<summary>Issues (1)</summary>

1. **Long-message URL length** — `convertScript` passes the full message text as a `?text=` query parameter. The Aksharamukha public API is a GET endpoint with no documented length limit; browsers and some CDNs enforce ~2000–8000 character URL limits. A long message or a long chat reply will silently fall back to the unconverted text (graceful degradation kicks in), but the user gets no indication the conversion was skipped. Consider truncating the text to a safe limit (e.g. 1500 chars) before building the URL, or surfacing a visual indicator when fallback occurs.

</details>

<details>
<summary>Details</summary>

### URL-length constraint on Aksharamukha calls

`convertScript` builds a `URL` object and sets `searchParams` for `source`, `target`, and `text`. For Rañjanā modes, both the user message and the AI reply each trigger a separate Aksharamukha GET request, so a 600-character message produces a URL on the order of 700+ bytes. The public API endpoint (`aksharamukha.appspot.com/api/public`) has no documented maximum, but the Chrome URL limit is ~32 KB and many proxies cap at 8 KB — so in practice this is only a concern for very long messages. The graceful-degradation catch means the UI won't break, but the user sees their original Devanagari text instead of Rañjanā without any warning. The fix is a pre-truncation guard or a fallback indicator in the UI.

### History capture in handleSubmit

`sendChatMessage` receives `messages` from the closure captured at `handleSubmit` call time. Because the user message is appended via `setMessages(prev => [...prev, userMsgWithDisplay])` before `sendChatMessage` is called, the history sent to the AI does **not** include the current user turn — only prior turns. This matches the spec's stated intent (`history: history.map(...)` maps `messages` state before the update) and avoids sending the in-progress message to the backend, so this is deliberate.

### Test coverage

All 6 required tests pass: the `source === target` short-circuit, the correct URL param construction, graceful degradation on fetch failure, the missing-endpoint error, the success path returning `reply`, and the invalid-response (no `reply` field) throw. The test for the URL params checks `toContain('text=')` but not the encoded value — sufficient for confirming the param is present.

Not tested: AbortError handling in `sendChatMessage` (a non-ok HTTP status from Aksharamukha returning original text), and the UI component behavior on mode switch mid-conversation.
